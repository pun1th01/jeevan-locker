# JeevanLocker — Testing

What the automated suite proves, how it proves it, and how to run it. Every claim below is backed by a test in `server/test/`; the claim IDs (C1, C2, …) are stable so the report can cite them. If a test and this file disagree, the test wins — fix this file.

Related: [ANCHORING.md](ANCHORING.md), [ENCRYPTION.md](ENCRYPTION.md), [EVENTS.md](EVENTS.md), [API_LAB.md](API_LAB.md), [API_ADMIN.md](API_ADMIN.md).

## 1. Running it

```bash
cd server
npm install
npm test                    # every suite, once
npm run test:watch          # re-runs on change
npm run typecheck:test      # strict type-check of src/ + test/
npm run verify:anchors      # separate fast check: ANCHORING.md §3 worked example (no DB, no chain)
```

**Prerequisites: none beyond `npm install`.** No `.env`, no running MongoDB, no running Hardhat node. The suite starts its own chain and database, generates its own keys, and ignores any `server/.env` you have. It never touches `server/uploads`, your dev database or a chain on port 8545.

First run on a fresh clone downloads two things once and caches them: the MongoDB server binary (mongodb-memory-server) and the Solidity 0.8.24 compiler (Hardhat). Everything after that is offline.

A run leaves the working tree clean. `server/artifacts/` and `server/cache/` are regenerated by the compile step and are gitignored.

## 2. How the harness works

```
npm test
 └─ global setup (once, main process)                       test/support/globalSetup.ts
     1. hardhat compile                                       no-op when artifacts are current
     2. hardhat node on a free random port  ║  mongod        in parallel; "ready" = it answers, never a sleep
     3. deploy DocumentRegistry + AuditAnchorRegistry from Hardhat account 0
     4. provide { chain, mongoBaseUri } to the workers
 └─ each test file (forked worker, fresh module registry)   test/support/perFile.ts
     - chdir into a new empty temp directory
     - pin the complete environment                          test/support/testEnv.ts
         own database on the shared mongod      jl_<worker>_<random>
         own DOCUMENT_MASTER_KEY and JWT_SECRET  random per file
         own funded chain account               Hardhat account #<worker>
     - import the app, connect, run tests
     - drop the database, delete the temp directory
 └─ teardown: stop mongod, kill the chain's process tree, wait for its port to close
```

**Why one chain and one mongod.** Measured on the development machine: a Hardhat node takes 3–4 s to answer (27 s on a cold machine), mongod 2 s (10 s cold). Per file, that would dominate the run.

**Why files still cannot interfere.**
- *Database:* one per file, dropped afterwards.
- *Chain nonces:* each worker signs with its own Hardhat account, so two files running in parallel never race for a nonce. Within a file, the server's own `sendSerialized` mutex applies, exactly as in production.
- *Chain state:* anchors and document registrations are keyed by fresh ObjectIds and content hashes, so the write-once contracts never see the same key from two files.
- *Files on disk:* `UPLOAD_DIRECTORY` is `cwd/uploads`, fixed at import, and every file has its own `cwd`.
- *Process state:* rate-limiter counters and module caches live in the worker's module registry, which is fresh for every file. `vi.stubEnv` changes are reverted after every test.

**Nothing the report claims is mocked.** Transactions go to real contract bytecode on a real node; documents are really encrypted to disk and read back; every request goes through the real Express app, middleware and database. The single shortcut is how test users are created: inserted directly with a cost-4 bcrypt hash instead of the pre-save hook's cost 12 (~300 ms each), and given tokens from the real `generateAuthToken`. Login itself is tested separately, through the real endpoint and limiter.

**Determinism rules the suite follows.**
- No fixed sleeps. Every wait is `waitFor(<named condition>)` and times out with that name.
- Time-based states are set, not waited for: a grant "lapses" because the test writes its `expiresAt` into the past, which is exactly the state the server acts on.
- Unique emails and ids per fixture; no test depends on another test's side effects or on run order.

### Harness guarantees (`test/harness.test.ts`)

These are not claims about JeevanLocker; they are what makes every other result trustworthy.

| ID | Guarantee | How it is checked |
|---|---|---|
| G1 | Every environment variable the server reads is pinned by the harness — a local `.env` cannot change a result. | Scans `src/` for `process.env.X` and for calls to the env helpers; fails naming any variable (and the file reading it) that `testEnv.ts` does not pin. Also fails if a new file reads `process.env[...]` dynamically, which the scan cannot see. Verified to fail when a pinned variable is removed. |
| G2 | Every variable documented in `.env.example` is pinned. | Parses `.env.example`. |
| G3 | Tests run from an empty temp directory: no `.env` is readable and uploads never touch `server/uploads`. | Checks `cwd`, the absence of `.env`, and where `UPLOAD_DIRECTORY` resolves. |
| G4 | Each file has its own database and its own funded chain account, never the deployer's. | Checks the connected database name and the signer's balance and index. |
| G5 | The chain is real. | `getCode` at both addresses; a real upload is encrypted into this file's workspace (`JLE1` header on disk) and its hash verifies against the chain through `/integrity`. |

## 4. What is not tested

- The React client. The suite is server-side; the UI was verified by hand in the browser for each feature.
- Timing side channels (e.g. whether the lookup 404 takes measurably longer for a non-patient email). Responses are compared for identical status and body only.
- Multi-process deployment. Rate limits use the in-memory store and the send mutex is per process, exactly as documented; a clustered deployment would need a shared store and a nonce manager.
